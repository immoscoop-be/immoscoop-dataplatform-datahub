- [ ] <a id="op-dh-56"></a>**OP-DH-56** · The query language of Data Hub: macros in the SQL, as dbt has them, so that dimensions and measures, and with them what a chart needs, are part of every query. *Raised on 2026-11-18, by Max, while working out the details of the fields of a Lens: "the query language should have/extend with 'functions' which deliver data in a way that semgraph is enabled … so basically the issues of dimensions and measures becomes an intrinsic part of datahub's query language and therefor very transversable"; on the direction worked out with Claude: "this is idd the direction I'm thinking of, perfect its kindof the macro language in dbt … we will need to iterate further on this language".* What stands so far:
  - **Field functions** declare a dimension or a measure and its kind, such as `datahub.category('Lead source', leadSource)`, `datahub.count('Credit leads')` or `datahub.ratio('Conversion', converted, requests)`; the first argument is the name users see. **Query parts** set the frame of a query, such as `datahub.timeline(events, datetime, windows => [7, 14, 28])` in its `from`: a sense of time, per day and per rolling window.
  - query expands them into plain BigQuery SQL before the Pre-flight, as it already puts a Parameter whose value is a function into the SQL ([DEC-UX-118](../design/principles.md#dec-ux-118)). Each column a function delivers is named by an ID that starts with a letter, never in backticks; Data Hub keeps what the ID stands for: its name, its kind, its arguments and its explanation. The grid, a chart, Excel and Claude show its name, never the ID.
  - The macro chooses the technique, not the author: a rolling window over a timeline of every day, a day without data counting as 0; a sum, a ratio and a stock roll with window functions, a unique count over a window does not and needs a join to the timeline.
  - **A graph always says when it ran and what it covers.** Every result of a timeline delivers the period as asked, the reference day, the last complete day at the run, never after the period, nothing after it, the bounds of each window, and when it ran; every graph of it shows the day it ran and the reference period. *Required by Max: "rolling window we need the info about 'on which day this has run and is the reference period' we need it in the graphs … don't know how semgrpah does it, i need it".*
  - It takes over the details of the fields of a Lens: the name users see, the kind of number, what one row is and the date that drives the period follow from the functions, not from a classification by hand.
  - To work out, a case at a time, each with the syntax, the SQL it expands into, what Data Hub keeps and the chart it feeds: rolling windows that add up (a first draft is made); calendar periods; unique counts; ratios; stocks; a comparison with the previous period and last year; categories, ordered or not; later averages and medians with their spread, and distributions. Also to decide: its domain, "Query language" of its own or under Query in [Stacks and resources](../requirements/functional/04-stacks-and-resources.md); copying as plain BigQuery SQL; the Query Log keeping the SQL as written and as expanded ([DEC-LN-01](../requirements/functional/07-log-and-notifications.md#dec-ln-01)); and errors of BigQuery pointed back at the function they come from.
