What to pick up next for Data Hub, in no fixed order. Each item is an open point: it says what was asked, and points to what is already decided or built that it starts from. Working an item out moves it into the domain file it belongs to, as requirements, decisions and open points of that domain; the item here is then ticked off, with a note of where it went.

The themes that were migrated from Confluence, or raised while taking in a workshop or a principle, stay in [Open themes](open-themes.md).

## Items

- [ ] <a id="op-dh-48"></a>**OP-DH-48** · Roles: defining a role enables certain features. Work out a section of roles in Data Hub itself: which roles exist, what each enables, and who gets one. Today a role comes only from a Role Group in Workspace, read at sign-in and at every renewal of the Access Token, every 15 minutes ([FR-UM-11](../requirements/functional/02-user-management.md#fr-um-11)); what a User may do with an asset follows from Owner, Reader and Data Admin ([DEC-DH-78](data-hub.md#dec-dh-78)). Roles kept in Data Hub would go into the same Access Token, so every service, the MCP server included, reads them as it does today. To decide: a role for a User, for a Group, or both; a fixed list of roles, each with one effect, or roles put together by hand; whether the role of the Data Team stays in Workspace, so that someone can give the first roles; and a Log of who gave or took which role, and when. *Raised on 2026-11-05, by Max, for the backlog.*
- [ ] <a id="op-dh-49"></a>**OP-DH-49** · Read access: work out how Data Hub gives different levels of read access. What a User sees follows from Collections and Owner Units alone ([DEC-DH-77](data-hub.md#dec-dh-77)), and Claude may read for them all they see, rows included ([DEC-CL-06](../requirements/functional/17-claude.md#dec-cl-06)). The first level asked for: some Users see the result of a query or a Preview in the MCP App, without its rows going into their Claude; for others, Claude works on the result as today. Which Users follows from the roles ([OP-DH-48](#op-dh-48)). What Max prefers for that level, on 2026-11-05: Claude still reads the shape of the result, its columns and their types, the number of rows, what it read, the Levels and the link, but none of its values; the values of the choices of a Preview stay out of Claude too; and the MCP App says that Claude does not read the rows. Its limits: the client of Claude, not Data Hub, hides the tools that only the MCP App calls ([DEC-CL-07](../requirements/functional/17-claude.md#dec-cl-07)); the User can still paste rows into the conversation; and the rows still pass through Anthropic on their way to the MCP App, only not into the conversation. *Raised on 2026-11-05, by Max, for the backlog.*
- [ ] <a id="op-dh-50"></a>**OP-DH-50** · Lens first: in Claude, when a User asks a question, the first suggestion is always a Lens. Decided as [DEC-CL-10](../requirements/functional/17-claude.md#dec-cl-10) and built as [FR-CL-17](../requirements/functional/17-claude.md#fr-cl-17): the tool `suggest_lenses`, which the server instructions ask Claude to call before it writes a query. It is an instruction Claude follows, not a rule Data Hub holds: `search` lists Collections, Resources and Lenses side by side, and `create_query` makes a query without looking for Lenses. To work out: how a Lens comes first every time, for example Lenses first in what `search` answers, or `create_query` answering with the Lenses on its Resources. *Raised on 2026-11-05, by Max, for the backlog.*
- [ ] <a id="op-dh-51"></a>**OP-DH-51** · Graphs: work out the graphs of Data Hub. In v1 a Lens shows a table and has no chart ([DEC-LE-08](../requirements/functional/09-lenses.md#dec-le-08)); visualisations come with [Reports](../requirements/functional/10-reports.md), still to be specified; the charts of semgraph are in Charts ([FR-CH-06](../requirements/functional/13-channels.md#fr-ch-06)). To decide first: which graphs, on which assets, and in which channels. *Raised on 2026-11-05, by Max, for the backlog.*
- [ ] <a id="op-dh-52"></a>**OP-DH-52** · Usage validations: define the rules that signal possible misuse, and who is alerted. The first rule: a Lens made in a Collection while none of the Resources it reads sits in that Collection hints that the wrong person is writing definitions. A Lens may read Resources of other Collections on purpose ([DEC-CO-20](../requirements/functional/03-collections.md#dec-co-20)), so such a rule signals and does not refuse. To decide: the rules, who gets the alert, such as the Data Team or the Owner Unit of the Collection, and how. *Raised on 2026-11-05, by Max, for the backlog.*
- [ ] <a id="op-dh-53"></a>**OP-DH-53** · Monitoring: work out the monitoring. Raised as "the monitoring"; to settle first whether it is the monitoring of the data, of Data Hub, or both. Of Data Hub itself, as a platform: [OP-PF-20](../requirements/technical/00-platform.md#op-pf-20). *Raised on 2026-11-05, by Max, for the backlog.*
